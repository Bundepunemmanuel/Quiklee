# Quiklee

Calculators, converters, and meanings — one real, static HTML file per search query, built for Vercel.

## Live structure (repo root)

```

converters.html                → converters hub page
meanings.html                   → meanings hub page

calculators/                     → FOLDER — one file per calculator, e.g.:
  bmi-calculator.html                → lives at /calculators/bmi-calculator
  pay-raise-calculator.html           → lives at /calculators/pay-raise-calculator
  ...21 more...

cm-to-feet-height-converter.html   → converters still FLAT at root (pre-folder phase)

lol-meaning-texting-vs-slack.html      → lives at /lol-meaning-texting-vs-slack
...3 more...

calculators-data.js        → source data: one entry per calculator (edit this)
converters-data.js          → source data: one entry per converter (edit this)
meanings-data.js             → source data: one entry per meaning (edit this)

page-template.html          → shell template for every tool page
hub-template.html            → shell template for the 3 hub pages
```

## Why calculators live in a folder and converters/meanings don't (yet)

Calculators were migrated to `/calculators/[slug]` for cleaner topical grouping in the URL.
Converters and meanings are still flat (`/kg-to-lbs-converter`) — not moved yet, just not done.
Same static-generation approach either way; only the URL shape differs. When it's their turn,
`build.js` already supports it — see the `folderized` flag on the `buildSection()` calls.

## What's on every calculator page now

- **`hook`** — one bold, concrete sentence with a real worked example, shown right under the H1
  (e.g. "A 175cm, 70kg adult has a BMI of 22.9"). Answers the query before the visitor even
  touches the form.
- **`titleHook`** — a short click-motivator in the `<title>` tag, e.g.
  `BMI Calculator | Find Your BMI Instantly`. Kept under 60 characters combined with the title
  so Google never truncates it. `build.js` warns at build time if any title/meta description
  exceeds Google's display limits (60 chars title, 160 chars meta description) — fix any
  warning before deploying.
- **`faq`** — 3–4 Q&A pairs per page, each phrased from a real long-tail search query (sourced
  from a Google Keyword Planner export), answered in plain language, matched to whether that
  phrase is tool-intent ("how do I calculate X") or info-intent ("what is a healthy X"). Rendered
  as real visible page content *and* as FAQPage JSON-LD schema for rich results.
- **In-body contextual links** — the `explainer` text uses `[[slug|link text]]` markers to link
  naturally to related calculators mid-sentence, not just in the bottom link list. Only added
  where there's a genuine, natural connection — not forced onto every paragraph.

## Adding a new calculator (you still never hand-write HTML)

1. Open `calculators-data.js`, copy an existing entry as a starting point.
2. Fill in: `slug`, `cluster`, `clusterLabel`, `title`, `titleHook`, `metaDescription`, `h1`,
   `hook`, `intro`, `type`, fields/content, `explainer` (using `[[slug|text]]` for natural
   in-body links), `caveat`, `faq`, and `related`.
3. If it's a new calculation type, add one `case` to the `calculate()` function in `main.js`.
4. Run `node build.js`. Watch the console for length warnings before you push.
5. Commit and push — Vercel runs the same build automatically (see Deploying below) and the
   new URL, its sitemap entry, and its FAQ schema all go live together.

## Deploying

1. Push this whole folder to a GitHub repo.
2. Import the repo in Vercel.
3. Set these two Build & Development settings in the Vercel project (Settings → Build &
   Development Settings):
   - **Build Command:** `node build.js`
   - **Output Directory:** `.`

   With this set, every `git push` triggers Vercel to run `build.js` on its own servers before
   deploying — regenerating every page, `vercel.json`, and `sitemap.xml` from whatever is
   currently in the `*-data.js` files. You never run the build yourself.
4. After it's live: add the site in Google Search Console, submit `sitemap.xml` once, and use
   the URL Inspection tool to request indexing for the first few pages manually.

## Keyword research so far

A Google Keyword Planner export (seeded on BMI, percentage, tip, pay-raise, and basic
converter terms) was used to validate real search phrasing and volume tier for the calculators
built so far. Note: Keyword Planner groups some near-duplicate/broad-match terms under the
same inflated volume number (e.g. "bmi calculator," "bmi cl," and "bio mass index" all showed
5,000,000/mo as one broad-match group) — treat volume as a rough tier, not a literal count.

## Not yet built (backlog)

- **Age & Date calculators** (Age Calculator, Date Difference, Days Between Two Dates, Day of
  the Week, etc.) — no keyword data collected yet for this cluster. Run a Keyword Planner
  export seeded on these terms before building, same process as the BMI/percentage clusters.
- **Remaining Financial calculators** (Loan EMI, Simple/Compound Interest, Profit Margin,
  Average, Ratio, Fraction, Square Root, GPA, Fuel Cost, Salary Hourly-to-Monthly, Inflation,
  Savings Goal, Markup, Grade %) — same: needs its own keyword export first. Fraction and
  Square Root skew toward a student audience rather than the money/adult intent of the rest of
  this cluster — worth a deliberate decision on whether they fit the site before building.
  Reverse Percentage Calculator and Percentage of a Percentage were flagged as likely too close
  to existing pages (percentage-difference, percentage-calculator) — don't build without a
  clearly distinct angle first.
- **Converters and meanings folder migration** — move `/kg-to-lbs-converter` style URLs into
  `/converters/kg-to-lbs-converter`, same pattern as calculators. `build.js` already supports
  this via the `folderized` flag; just flip it on for those two `buildSection()` calls when
  ready and delete the old flat files.
- **Comparisons section** (software/app/product comparisons) — phase 2, not started.
- **Ad/affiliate placements** — left out of the markup entirely for now. When ready, slots
  should go in `page-template.html` so every page gets them at once — positioned above/below
  the tool card, never inside or blocking it.
